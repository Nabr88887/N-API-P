## 开始前

- [ ] 明确试点负责人、值守联系人、开始/结束时间、参与者名单和停止决策人；首轮建议不超过 5 名自愿内部测试者，具体名单与人数写入试点批准。
- [ ] 固定不可变源代码 revision、镜像 digest、配置版本和构建清单；确认构建产物对应同一 revision，工作区无未审查改动。
- [ ] 对该 revision 取得新鲜的 Go、前端、lint、类型检查、构建和安全验证结果；E2E 与集成检查按其实际批准和运行状态注明，不以静态检查替代。
- [ ] 完成安全与代码审查，确认无未解决的发布阻断项；核对凭据不在代码、镜像层、日志、工单或截图中。
- [ ] 任何 NewAPI 测试 token 必须是专用项目 token，模型范围、有限额度、有效期、撤销路径和受保护的文件载体均已核验。现有专用 token 经独立切换后仅限 Pro；沿用原有额度和到期边界，不自动新建、补额或续期。历史 Gate C 批准本身不授权试点流量。
- [ ] 明确数据边界和保留期限。默认使用合成请求；真实员工提示词、响应或身份数据须由准确的独立范围明确批准。
- [ ] 核对 PostgreSQL 备份可读、恢复步骤与负责人已确认；迁移影响、兼容性和恢复点已评估。不得将破坏性降级迁移作为回滚手段。
- [ ] 核对员工入口保持关闭直到验收通过；N-API-P 到内部 proxy 使用证书校验 HTTPS，proxy 到 NewAPI 的 HTTP 仅允许位于已验证私有且未发布的容器网络。
- [ ] 将试点期间可观察的健康、错误、延迟、审计完整性、限流和资源指标，以及基线来源写入批准记录；若缺少可比较基线，停止扩量并先补齐观测。
- [ ] 试点批准明确允许的服务生命周期、数据库操作、入口变更、测试账号/数据、回滚执行人和清理范围。不得从本清单或 Gate C 批准推导这些权限。

## 执行顺序

1. 复核批准仍有效、目标与数据匹配，记录 revision、镜像 digest、配置版本、备份标识和开始时间。
2. 按批准执行变更；入口保持关闭，直到数据库兼容性、服务健康和 operator 权限检查通过。
3. 验证 Docker health、`/health/live`、`/health/ready`、未登录拒绝、低权限隔离和管理员登录/退出。
4. 仅对获准参与者运行批准的测试流量；验证模型策略、个人用量、限流、完整审计元数据和内容保留行为。
5. 观察批准记录中的指标和停止条件。只有全部通过且负责人签字后，才可按该批准的范围开放小组入口；扩大人员、流量、数据或时间都需要更新范围。
6. 试点结束后关闭入口，按批准撤销专用测试凭据和临时权限，保留无内容的结果记录，并核对资源清单。

## 停止条件

出现以下任一情况，立即停止新增流量并关闭内部入口；不得继续扩量：

- 认证或授权绕过、跨用户/团队数据可见、NewAPI 或员工凭据暴露、敏感内容进入日志。
- 已完成请求缺失审计/用量记录，审计写入门失效，或过期内容仍可读取。
- 数据库/key/upstream 故障导致 fail-open、状态无法核对或请求结果无法安全归属。
- 健康检查持续失败、错误或延迟超过批准阈值、限流失效，或观测数据不足以判断影响。
- 变更超出批准范围、批准失效，或需要未批准的迁移、权限、配置、数据或服务操作。

## 回滚顺序

1. 关闭内部 proxy 入口并停止新请求；保留无提示词、响应、token 或认证头的诊断证据。
2. 按批准将应用切回上一个已核验的不可变镜像 digest；不得用可变 tag 猜测上一版本。
3. 保留数据库现状，不执行破坏性 down migration。若旧镜像与新 schema 不兼容，保持入口关闭，按单独批准的备份恢复流程处理。
4. 若凭据可能泄露，按批准的撤销/轮换范围处置；不要把员工流量切换到 NewAPI 凭据。
5. 验证 Docker health、`/health/live`、`/health/ready`、登录拒绝/授权边界、审计和用量状态，并确认入口仍处于预期状态。
6. 记录 revision、镜像 digest、触发条件、时间、稳定错误码、恢复结果和遗留风险；不记录原始请求/响应或秘密值。
